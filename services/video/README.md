# Video service

Отдельный процесс записи. Hub хранит настройки камер в SQLite. Этот сервис их забирает и на каждую включённую камеру с RTSP URL запускает свой `ffmpeg`. Кадры в Python не декодируются. Modbus-воркеры этот процесс не делят.

Автоочистка каталога и детекция человека сюда не входят: сервис только режет поток на фрагменты.

## Контракт

- `GET /api/v1/cameras` и `PUT /api/v1/cameras` — страница администратора.
- `GET /api/v1/internal/video/config` — то, что читает рекордер. Заголовок `X-Video-Token` равен `BB_VIDEO_TOKEN`.
- `POST /api/v1/internal/video/status` — короткий статус по камерам: `recording`, `stopped` или `error` и хвост stderr.

Тело конфига — список камер. У каждой: имя, RTSP URL, роль потока `main`/`sub`, транспорт `tcp`/`udp`, разрешение (исходное, 3840×2160, 1920×1080, 1280×720, 640×480 или своё), FPS (пусто — как у камеры, иначе 1…60), кодек `libx264`, `libx265`, `mjpeg`, `copy` или `h264_v4l2m2m`, профиль H.264, preset, битрейт кбит/с, интервал ключевого кадра, звук `none`/`aac`/`copy`, контейнер `mp4`/`mkv`, длительность фрагмента в секундах.

`copy` не ставит `scale` и `fps`: в файл попадает поток камеры. Битрейт в этом режиме нужен только для оценки размера.

Файлы: `/data/video/<camera_id>/%Y%m%d_%H%M%S.mp4` (или `.mkv`).

Оценка размера, одна и та же на странице и в API:

`МиБ = (video_kbps + audio_kbps) × секунды / 8 / 1024`

Считается фрагмент, час и сутки. Для кодека `copy` это оценка по введённому битрейту, ffmpeg его не ограничивает.

Образ ставит сборку ffmpeg с libx264, libx265 и AAC, а не урезанный пакет Debian.
